# CI lessons, week 2026-W46

Patterns in test code that made CI flaky this week, and how to avoid them.

## 1. Stop every client before you restart the service it calls

Restarting nodes in the middle of a suite is safe only if nothing else is still talking to them. Nodes left running
keep calling the restarted service. Their retry budgets were sized for a short blip, not for a stop followed by a full
initialization.

Example: a test restarted all SV and scan nodes, but two validators started by an earlier test case stayed up. Their
scan clients retry a failed call 12 times over about 7 s. A scan refuses connections while it is stopped and answers
404 while it initializes, which took longer than that. The validators gave up and logged warnings, and those failed
the log check.

Do: stop the callers first, restart, then bring the callers back.
```scala
(callers ++ restarted).foreach(_.stop())
restarted.foreach(_.start())
callers.foreach(_.start())
```

## 2. Give a wait more time than one attempt of the request it retries

`eventually` and `eventuallySucceeds` retry only between attempts. If a single attempt can take longer than the whole
budget, the budget runs out during the first attempt and there is no retry at all. The test then reports the
request's own timeout, even though a second attempt would have worked.

Example: a validator onboarding call was wrapped in `eventuallySucceeds()`, whose default budget is 20 s. The call hit
the validator's 38 s server request timeout. By the time that error came back, the budget was spent, so it was
rethrown without a second attempt. The handler itself finished with 200 OK 17 s later. It was slow because right after
a multi-SV BFT onboarding, every ledger transaction needed three sequencing hops of 2 to 4 s each.

Do: size the budget from the slowest single attempt (the server's request timeout, or the expected latency of the
transactions behind the call), with room for at least one retry.
```scala
// the server times out a request after 38 s: allow for a retry
eventuallySucceeds(timeUntilSuccess = 2.minutes) {
  validatorBackend.onboardUser(userName)
}
```

## 3. Poll a state that background automation can change

Reading a connection state, a store row or a config value once races with any automation that changes it. The read
is right most of the time, and wrong whenever it lands in the middle of a change.

Example: right after an SV joined, a test read the participant's connected synchronizers once. At that moment the
validator's reconnect trigger was disconnecting the participant to add a newly announced sequencer. The disconnect
came 190 ms before the read and the reconnect 65 ms after it.

Do: assert inside `eventually` (or the check of `actAndCheck`), so a transient value is retried until the steady
state holds.
```scala
eventually() {
  participant.synchronizers.list_connected().map(_.synchronizerAlias) should contain(globalAlias)
}
```

## 4. Pause automation on every node that runs it, and resume it in a `finally`

Most SV and validator automation runs on every SV or validator, not just on one. Pausing one copy leaves the others
free to do exactly what the test wants to hold back. A pause that is not undone in a `finally` also stays in place
for every later test case in the shared environment once the test fails.

Example: a frontend test needed an expiring vote request to stay open while it checked the UI, and paused the
close-vote trigger on sv1 only. When the UI steps took longer than the 10 s expiry, another SV closed the request
first. In another test, faucet coupon automation kept creating transactions between a "nothing new yet" check and the
action that followed. The fix paused that automation and took a fresh cursor on every attempt of the check.

Do: pause on all nodes. `setTriggersWithin` resumes in a `finally` for you.
```scala
setTriggersWithin(
  triggersToPauseAtStart = allSvs.map(_.dsoDelegateBasedAutomation.trigger[CloseVoteRequestTrigger])
) {
  // steps that need the vote request to stay open
}
```

## 5. Put ScalaTest tags on the concrete test classes

ScalaTest tag annotations are not `@Inherited`. A tag on an abstract base class does nothing for the classes that
extend it, so tag-based filters still run them. That includes the compatibility runs that skip tests needing a newer
Daml package.

Example: the base class of a group of reward tests carried the tag for the package version they need, but the
concrete classes did not. The nightly run against the older mainnet Daml packages ran them anyway. SV bootstrap then
set a config field the older package cannot hold, and the SV app failed to start every night.

Do: annotate each concrete class.
```scala
abstract class RewardsTestBase extends IntegrationTest

@SpliceAmulet_0_1_25
class RewardsDryRunTest extends RewardsTestBase
```

## 6. Give a replacement node its own endpoint while its predecessor may still be running

A node that a test re-creates (a re-onboarded SV, a successor) often reuses its predecessor's port. If the
predecessor is still running, or its peers still remember it, the peers can tie the old identity to the reused
address.

Example: a re-onboarding test offboarded an SV and started its replacement on the same sequencer P2P port. The old
sequencer was still running for a few seconds, reconnected after its endpoint had been removed, and was authenticated
again under its old id. The peers kept that connection and attached it to the new node's id, so every message for the
new sequencer went to the old one. The new SV never finished initializing.

Do: give the replacement a port no other node in the test uses. If it has to reuse the port, stop the old node and
wait until the peers have dropped it before starting the replacement.

## 7. Find the element again on every retry

In Selenium, an element handle points to one DOM node. When React replaces that node, every later call on the handle
throws `StaleElementReferenceException`, and retrying the call with the same handle cannot succeed. React replaces
nodes on a re-render after a debounced lookup, or when a component renders a different tree while it is loading.

Example: a test typed a name and clicked the search button. The name's 500 ms debounce started a lookup during the
click, and the button's wrapper rendered a different tree while the lookup was loading. The button found before the
click no longer existed.

Do: look the element up inside the retry, and retry until the result of the click shows, not just until the click
returns.
```scala
eventually() {
  find(id("search-entry-button")).value.underlying.click()
  find(id("search-result")) should not be empty
}
```
