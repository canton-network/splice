# CI lessons, week 2026-W45

Patterns in test code that made CI flaky this week, and how to avoid them.

## 1. Know what advances the thing you wait on

A wait like `eventually { store shows X }` only works if something guarantees the store will move past X. Many
splice stores and streams advance on a signal other than the one your action produces.

Example: scan's `/v0/events` serves events only up to the minimum of the last ingested verdict and the last ingested
update record time. A transaction the DSO party cannot see produces a verdict but no DSO-visible update, so the stream
does not move past it until the next DSO-visible transaction. In a quiet test environment that can take longer than
any timeout; the test then passes only when unrelated background automation happens to run in time.

Do: before waiting, ask what advances the reader, and make sure your test causes it. For scan's event stream, follow
a private action with a DSO-visible one (a tap is enough):
```scala
actAndCheck(
  "private action, then a DSO-visible tap so the event stream moves past it",
  {
    privateAction()
    someWalletClient.tap(1.0)
  },
)("the reader sees the private action", _ => ...)
```

## 2. Match every label that splits a metric into series

A metric with labels is several time series. Console `metrics.get` requires exactly one series to match the given
attributes, so a lookup that leaves out a distinguishing label works only while one series happens to exist.

Example: `trigger.completed` has one series per `outcome` (`success`, `noop`, `fail`, `stale`, ...). A periodic
trigger records `success` when it does work and `noop` on the next idle poll, possibly without any log line. A
lookup by `trigger_name` and `party` alone passes before the first idle poll and fails for good after it.

Do: include every label that identifies the series you mean:
```scala
backend.metrics.get(
  s"$MetricsPrefix.trigger.completed",
  Map("trigger_name" -> triggerName, "party" -> party.toString, "outcome" -> "success"),
)
```
More generally: a test that passes only because it ran before the next background poll has a timing bug. Ask what
the system does in the next 30 s, not only what it has done so far.
