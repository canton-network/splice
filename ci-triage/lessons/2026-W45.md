# CI lessons, week 2026-W45 (2026-11-02 to 2026-11-08)

Test-code patterns behind this week's CI failures, for the engineers maintaining splice. Each lesson: what we saw,
why, and how to write it so it does not flake.

## 1. Scan's event stream only moves when the DSO party sees something

**Seen:** `ScanPartyMonitorScriptIntegrationTest` failed 5 times in 2 days (#11128, #11136, #11138, #11139,
#11158). The test made a transfer offer the DSO party does not see and waited 20 s for `/v0/events` to serve its
verdict. It never did.

**Why:** `/v0/events` serves events only up to min(last ingested verdict, last ingested update) record time
(`ScanEventStore.getCurrentMigrationCap`). A private transaction produces a verdict but no DSO-visible update, so the
cap stays where it was until the next DSO-visible transaction. In a 1-SV test environment that can take longer than
any reasonable timeout; the test only passed when unrelated automation happened to run in the window.

**Do:** after a transaction the DSO party cannot see, cause one it can see before you wait on scan's event stream
(a tap is enough), so its record time is after the one you wait for:
```scala
actAndCheck(
  "Alice offers bob a transfer, which the DSO party does not see, followed by a DSO-visible tap",
  {
    aliceWalletClient.createTransferOffer(bobParty, 2.0, "private offer", expiry, UUID.randomUUID.toString)
    aliceValidatorWalletClient.tap(1.0)
  },
)("The script reports alice confirming the private transaction", _ => ...)
```
More generally: before waiting for a store or stream to show something, check what actually advances it.

Fix: #8211.

## 2. Look up a metric by every label that splits it into series

**Seen:** `WalletMetricsTest` failed with `Found 2 matching metrics` for 20 s (#10732, #11143).

**Why:** `trigger.completed` has one series per `outcome` label (`success`, `noop`, `fail`, ...). Console
`metrics.get` requires exactly one matching series. A periodic trigger such as the per-party DomainIngestionService
records `success` on its first poll and a silent `noop` on the next one (24 to 36 s later), so a lookup by
`trigger_name` and `party` alone passes or fails depending on when the test gets there. Once the second series
exists, `eventually` cannot recover.

**Do:** include every label that distinguishes the series you mean:
```scala
aliceValidatorBackend.metrics.get(
  s"$MetricsPrefix.trigger.completed",
  Map("trigger_name" -> triggerName, "party" -> aliceUserParty.toString, "outcome" -> "success"),
)
```
A test that passes only because it ran before a background poll is a timing bug. Ask what the system will do
during the next 30 s, not just what it has done so far.

Fix: branch `rautenrieth-da/fix-10732-wallet-metrics-outcome-label` (PR pending).
