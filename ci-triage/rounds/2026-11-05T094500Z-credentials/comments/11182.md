Scan bug, false ERROR: the BFT check in BulkStorageCommitFromStaging runs once more after it has already succeeded, and that extra check fails when a peer has meanwhile committed the segment and deleted its staging copy.

checkErrors flagged one line in ScanNewNetworkBackfillingTimeBasedIntegrationTest; all tests passed.

```
07:31:03.484 [sv2Scan] BFT agreement reached for the objects of UpdatesSegment(1970-01-03T00:00:00Z,1970-01-04T00:00:00Z). Proceeding with commit.
07:31:03.488 [sv2Scan] POST /api/scan/v0/history/bulk/checksums (second request for the same two objects)
07:31:03.498 [sv1Scan] Deleted object 1970-01-03T00:00:00Z~1970-01-04T00:00:00Z/updates_protobuf_json_0.zstd from staging storage
07:31:03.541 [sv1Scan] Responding with entity data: {"checksums":[{"value":"nug+...="},{"value":null}]}
07:31:03.542 [sv2Scan] Not all objects are known to the BFT peers, despite them indicating that they have caught up to the required timestamp. ...
```

sv2Scan committed the segment at 07:31:03.539 based on the first check; the ERROR comes from the second one. `waitForBftAgreement` runs the check as `Source.repeat(obj).mapAsync(parallelism = 1)(...)` followed by `takeWhile(!bftReached, inclusive = true)`, and mapAsync starts the next check as soon as the previous one completes, before takeWhile sees the success. On a cluster this gives the same false ERROR whenever a peer commits the segment within one check.

Fix: no check after a successful one, e.g. a Future-based retry loop or `Source.unfoldAsync` that ends on success, instead of `Source.repeat` + `mapAsync` + `takeWhile`.
