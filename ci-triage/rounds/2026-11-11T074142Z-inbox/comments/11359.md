These failures come from the PR. The new `FeaturedAppConfigUpdateInstruction` filter in the `SvDsoStore` ACS filter breaks SV1 bootstrap on old package versions.

Every failing shard (`resource-intensive (0)`, `wall-clock-time (4)`, `wall-clock-time (5)`, in both attempts) first fails in a test that bootstraps the network on the minimum package config: `BootstrapPackageConfigIntegrationTest`, `BootstrapPackageConfigDarUploadIntegrationTest` and `BootstrapPackageConfigDarUploadWithUnsupportedVersionsIntegrationTest`. Those versions include a `splice-dso-governance` without `Splice.DSO.Instruction` (the template was added after the 0.1.31 bump), so the participant rejects the DSO store's ACS request. Checked in the logs of resource-intensive (0), attempt 1 (canton.clog); the wall-clock shards fail at the same point (SV app init, then teardown), but their logs were not checked for this line:

```
2026-11-11T12:39:37.443Z Request com.daml.ledger.api.v2.StateService/GetActiveContracts by grpc:/127.0.0.1:52746: failed with NOT_FOUND/NO_TEMPLATES_FOR_PACKAGE_NAME_AND_QUALIFIED_NAME(11,1f382e6b): The following package-name/template qualified-name pairs do not reference any template-id uploaded on this participant: [(splice-dso-governance,Splice.DSO.Instruction:FeaturedAppConfigUpdateInstruction)]. ...
```

The store retries this until the test gives up: 13 rejected requests from sv1Participant between 12:39:37 and 12:43:54. Meanwhile sv1 waits in `Ensuring that the DsoRules and AmuletRules are bootstrapped` (`waitUntilAcsIngested`), sv3 gets 404 from `/api/scan/v0/dso` while joining, and the test fails with `Timeout while waiting for initialization of sv3` at 12:44:23.

In `wall-clock-time (4)` and `(5)`, all later failures in the shard are follow-on failures, not separate flakes. The teardown of the first test throws in `UpdateHistorySanityCheckPlugin` (`The app state of sv2Scan is currently not accessible`), the environment leaks, and every later test fails with `Could not create Prometheus HTTP server` / `Address already in use` (the same cascade as #11347).

The other two failed jobs in attempt 1 are unrelated, and both passed in attempt 2: `key-download (0)` (two `onboard/sv/sequencer` 38 s timeouts, #11255) and `simtime (0)` (`Executing the custom container implementation failed`, runner).

Fix: give the new `mkFilter(FeaturedAppConfigUpdateInstruction.COMPANION)` in `SvDsoStore` a `versionGuard`, as the `RewardCouponV2` filter does with `supportsTrafficBasedAppRewards`. The guard needs a new `PackageVersionSupport` check for the `splice-dso-governance` version that introduces the template; `supportsTbarV1_1` checks splice-amulet, not dso-governance. The two new triggers should only run once that version is vetted as well.
