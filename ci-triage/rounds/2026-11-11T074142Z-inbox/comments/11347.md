Only the first failure is real: in `SvReonboardingIntegrationTest` the sv1 SV app was still initializing when `startAllSync` gave up after its 5 minute `waitForInitialization`. The other five tests fail because the first test's teardown threw and leaked its environment.

```

00:28:22.912 Ensuring that SV1 has uploaded the initial set of packages

00:31:38.736 Ensuring that the DsoRules and AmuletRules are bootstrapped
```

Most of the time went into DAR uploads: 87 uploads in 190 s, 7.5 s each on average on the participant. 22 of the 87 repeat a package that was already uploaded, the same repeated-upload pattern as #11299. The rest of the 5 minutes went into participant startup (25 s), loading package signatures (32 s) and the domain bootstrap (25 s).

Teardown then failed in `UpdateHistorySanityCheckPlugin.beforeEnvironmentDestroyed`:

```
java.lang.RuntimeException: The app state of sv2Scan is currently not accessible. Node doesn't have any app state.
  at ...ScanAppBackendReference.automation(ScanAppReference.scala:970)
  at ...UpdateHistorySanityCheckPlugin.$anonfun$beforeEnvironmentDestroyed$4(UpdateHistorySanityCheckPlugin.scala:58)
```

The plugin selects scans with `is_initialized`, which is true once the node is running. sv2Scan was still in `Get primary party` because sv2 waits for sv1, so it had no app state yet. The vendored `EnvironmentSetup.manualDestroyEnvironment` calls `beforeEnvironmentDestroyed` outside its `try`, so the exception skipped `environment.close()`. The leaked nodes kept logging until the end of the shard and kept their ports, so every later test failed with `Creating environment failed at step Creating fixture` / `Could not create Prometheus HTTP server` / `BindException: Address already in use`. The same cascade has followed other teardown failures before (#6275, #7150, #8982, #10176).

First failure of this shard: `key-download (0)` passed in the 22 other post-merge runs on main since 2026-11-09.

Possible fixes:
- Teardown: only check scans whose app has finished initializing in `UpdateHistorySanityCheckPlugin` (for example HTTP health active, not just `is_initialized`), so that a test failing during init still closes its environment. A more general fix is to run `beforeEnvironmentDestroyed` inside the `try` in `manualDestroyEnvironment` (Canton code change).
- Init time: deduplicating the DAR upload list (#11299) removes a quarter of the uploads. Whether that alone would have been enough here is not clear, because the DsoRules bootstrap was still running at the timeout. A longer wait for this test's `startAllSync` is the fallback.
