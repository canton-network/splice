## Cause: three large CI jobs packed onto one node

The node was short on CPU in exactly that window: its VM CPU utilization (Cloud Monitoring, per minute) was 58% at 18:45, then 79%, 91% and 93% at 18:46-18:48, 74% at 18:49, and 41% at 18:51. Three large CI workflow pods ran on it, each using 5 to 7 cores and about 30 GB of memory (together about 90% of the allocatable memory: 70% non-evictable, 20% evictable). Which job the third pod ran was not identified.

How three large jobs end up on one node:

- The runner node pool uses `c3d-standard-8` nodes (8 vCPU, 32 GB), with `c4-standard-32` and `n4-standard-32` (32 vCPU, 128 GB) as fallbacks. Three pods with about 30 GB each cannot run on a 32 GB node, so this node was one of the 32 vCPU fallbacks (inferred; the machine type is not in the metrics export).
- Large jobs also run on `c3d-standard-8` nodes, so their resource requests are at most what fits there. On a 32 vCPU node the scheduler can therefore place three or more of them.
- The scheduler only sees the requests of the runner pod; the workflow pod that runs the tests requests almost nothing and is only bounded by its limits (`cluster/pulumi/gha/src/runners.ts`, note on resource requests and limits). Whatever the workflows use above the requests is not accounted for when jobs are placed.

Not explained: the three workflow pods used about 15 to 21 cores, while the VM showed about 30 of 32 vCPU busy. Whether other pods ran on the node or the kernel spent CPU reclaiming memory was not checked.
