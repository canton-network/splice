Canton BFT P2P bug: after sv4 is re-onboarded with a new sequencer id on the same P2P endpoint, the other sequencers keep that endpoint bound to the old sv4 sequencer id, so the new sv4 sequencer never gets past its onboarding state transfer and the sv4 SV app never finishes initializing.

`SvReonboardingIntegrationTest` failed at the second `startAllSync` (`Timeout while waiting for initialization of sv4Reonboard`, 5 min). Package uploads took 30 s; the rest of the time the SV app sat in `Waiting until Mediator has been granted unlimited traffic`, which reads from its own new sequencer. sv1 to sv3 granted that traffic at 14:18:58, but the new sequencer never processed another block:

```
14:19:05.699 Starting Onboarding state transfer from epoch 81
14:22:46.886 Retrying block transfer request for epoch 81                      (55 times)
14:22:46.887 Not enough authenticated and whitelisted nodes available ... among List(SEQ::sv1..., SEQ::sv3..., SEQ::sv2...)   (53 times)
```

On the peers, the sequencer of sv1 authenticates the new node and binds port 27410 to it, then 105 ms later a leftover connection actor for the old sv4 id binds it back; this flips 868 times each way until the shutdown, and every message to the new node is dropped:

```
14:19:07.150 Associating P2P endpoint P2PUrl("http://localhost:27410") to BFT node ID SEQ::sv4ReonboardSvReonboarding::..d4da: Endpoint ... was previously associated with SEQ::sv4SvReonboarding::..06d6, changing to SEQ::sv4ReonboardSvReonboarding::..d4da
14:19:07.255 Associating P2P endpoint P2PUrl("http://localhost:27410") to BFT node ID SEQ::sv4SvReonboarding::..06d6: Endpoint ... was previously associated with SEQ::sv4ReonboardSvReonboarding::..d4da, changing to SEQ::sv4SvReonboarding::..06d6
14:22:52.294 Dropping network message to unknown SEQ::sv4ReonboardSvReonboarding::..d4da (possibly unauthenticated as of yet)
```

That leftover actor comes from the offboarding: the SVs removed the endpoint of the old sv4 at 14:17:21.395, the old sv4 sequencer (still running until its Canton was stopped at 14:17:27) reconnected 0.5 s later and was authenticated again under its old id. The new sv4 Canton reuses port 27410. sv2 and sv3 show the same pattern.

This is the symptom of #10011 on the ciperiodic SV re-onboarding ("other SVs still keep the old sequencer id"), which was closed as fixed in Canton 3.6 by DACH-NY/canton#35711. This run used Canton 3.7.3-snapshot.20261109, so either that fix does not cover a node that reconnects after its endpoint was removed, or it regressed.

Rare so far: first failure of `key-download (0)` with this cause in 46 post-merge jobs since 2026-11-09. Test-side mitigation if needed: stop the old sv4 nodes before the offboard vote takes effect, or give the re-onboarded sv4 sequencer a different P2P port.
