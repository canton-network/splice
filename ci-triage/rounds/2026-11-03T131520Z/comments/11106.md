The ciperiodic deploy_sv_reonboard deployment fails to render the validator Helm chart since canton-network/splice#8137 (Restrict allowed origins for the validator API without auth, merged 2026-10-30 09:28 UTC). This issue is the first failure; the later runs (#11137, #11142, #11151, #11171, #11183) are closed as duplicates.

In every attempt of step Apply Pulumi configuration to cluster that is in the job output (this run, #11137 and #11183), the validator1 stack fails to render:

```
[organization/validator1/validator1.ciperiodic] - error - error: execution error at (splice-validator/templates/validator.yaml:324:12): allowedOrigins must be set when disableAuth is true
```

canton-network/splice#8137 added this check to `cluster/helm/splice-validator/templates/validator.yaml`:

```
{{- if .Values.disableAuth }}
{{- if not .Values.allowedOrigins }}
{{- fail "allowedOrigins must be set when disableAuth is true" }}
```

but changed nothing under `cluster/pulumi`. Pulumi still passes `disableAuth` to the validator chart for validator1 (`cluster/pulumi/common-validator/src/validator.ts`, `disableAuth: baseConfig.disableAuth || false`; per its config, disableAuth is only honoured for validator1) and never sets `allowedOrigins` on that chart, so a deployment that runs validator1 with `disableAuth: true`, as sv_reonboard does, can no longer be rendered. No fixture in `cluster/expected` uses `disableAuth: true`, so the Pulumi snapshot tests did not catch it. The splice commits deployed by this run (76e1efc724) and by #11137 (e4825eacda) both contain it.

Fix (Pulumi): when `disableAuth` is set, pass `allowedOrigins` to the validator chart (for validator1 the origins of its wallet and ANS UIs), and add a `cluster/expected` fixture with `disableAuth: true` so the combination is rendered in CI. Assigned to @OriolMunoz-da as the author of canton-network/splice#8137.
