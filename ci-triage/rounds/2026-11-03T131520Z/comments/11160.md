Flake from write contention in the reference sequencer driver of the test setup; it makes wallet onboarding give up. Related: #10139, #10197, #10273 (same contention, different symptoms).

TokenStandardCliTestDataTimeBasedIntegrationTest (expire amulet allocations handling both locked and already unlocked amulets) on release-line-0.10.0 0ad3ce0394, simtime (2), failed in its first step, `onboardWalletUser` for alice on aliceValidator:

```
12:29:23.611 HTTP 400 Bad Request POST at '/api/validator/v0/admin/users' on 127.0.0.1:5503. Command failed, message: INVALID_PRESCRIBED_SYNCHRONIZER_ID(9,7a61b839): Not all informees are on the specified synchronizer: global-domain::122088c38f7c...::37-0, but on Set(splitwell::12205850d0f6...::36-0)
```

The new party of alice became effective on splitwell at 12:29:15.85, but on the global synchronizer only at 12:29:27.6, because globalSequencerSv1 could not store the topology broadcast it received at 12:29:14.922 for 13 s. `installWalletForUser` (ValidatorUtil.scala) submits on the global synchronizer and gave up at 12:29:23.526 (`Total maximum number of retries 12 exceeded`), 4 s before the party arrived.

## Why globalSequencerSv1 could not store it

The reference driver orders requests through one `blocks` table shared by the four global sequencers. Each batch is inserted under SERIALIZABLE isolation with the height computed inside the insert (Canton 3.7.1, `DbReferenceBlockOrderingStore.insertRequest`):

```
insert into blocks (id, request, uuid) values ((select coalesce(max(id) + 1, 0) from blocks) , $1, $2) on conflict (uuid) do nothing
```

Every two overlapping inserts conflict. The Postgres log of the job (GCP, container `postgres` of the runner pod) has 94 aborts between 12:29:05 and 12:29:28, all of this kind, and in 26 of 58 collisions 2 or 3 of the 4 writers were aborted at the same instant:

```
12:29:14.914 UTC [2090] ERROR:  could not serialize access due to read/write dependencies among transactions
12:29:14.914 UTC [2090] DETAIL:  Reason code: Canceled on identification as a pivot, during write.
```

This is routine in the shard (2936 failed inserts for 9508 stored batches; 99 percent of retry chains end within 0.5 s, no other insert lost more than 4 retries in a row). Here the insert of globalSequencerSv1 lost 8 retries in a row while the other three kept inserting, and its backoff grew past 1 s:

```
12:29:16.974 DbStorageSingle:sequencer=globalSequencerSv1 The operation 'insert block' has failed with an exception. Retrying after 1.31s.
12:29:18.827 DbStorageSingle:sequencer=globalSequencerSv1 The operation 'insert block' has failed with an exception. Retrying after 2.169s.
12:29:21.166 DbStorageSingle:sequencer=globalSequencerSv1 The operation 'insert block' has failed with an exception. Retrying after 6.373s.
12:29:27.587 SequencedSubmissionsValidator:sequencer=globalSequencerSv1 At block 6840, the submission request 624b7da8-22a0-4d4d-858b-76327b7fa692 at 1970-03-06T03:01:14.002287Z validated to: Deliver
```

Two details of the driver make this worse than intended:

- The test config caps storage retries at 1 s for exactly this case (`timeouts.processing.storage-max-retry-interval = 1s` in `canton-basic.conf`, canton-network/splice#5173), but the reference driver does not get the node timeouts: `ReferenceSequencerDriverFactory.create` builds its own `ProcessingTimeout()` with the defaults (`maxRetryInterval` 10 s). The three delays above are uncapped equal-jitter doubling from 50 ms; all other storage retries in the run stayed below 1 s (one participant lock check aside).
- Each driver inserts an empty block every 500 ms (`emptyBlockIntervalMillis`, default `Some(500)`) whether or not there are requests, so four sequencers write at least 8 conflicting rows per second even when idle.

Not a missing backport: the commit under test only changes a Grafana dashboard, and main has no change to ValidatorUtil.scala or the test since the release line branched. The load at 12:29 was not unusual: the abort rate rises through the shard (0 before 12:20, 69 percent of stored batches at 12:31 without failures) independent of the request rate.

## Possible fixes

- Canton (reference driver): pass the node timeouts to the driver storage, so the existing 1 s cap applies (8 lost retries would then take about 4 s instead of 13 s); or stop computing the height with `max(id) + 1` inside a SERIALIZABLE transaction.
- Test config: raise `sequencer.config.empty-block-interval-millis` for the reference sequencers to cut the idle inserts; whether a longer empty-block interval delays anything in the tests is not checked.
- Validator app (owner to decide): in `ValidatorUtil.onboard`, wait until the PartyToParticipant of a newly allocated party is effective on the AmuletRules synchronizer before `installWalletForUser`; this also covers slow ordering in production.

Not checked: why the insert of globalSequencerSv1 lost 8 retries in a row (the Postgres log does not show which backend belongs to which sequencer).
