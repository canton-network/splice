## Upcoming for next patch release:

{/* Add all release notes in this section */}

  - Health checks of Canton nodes

    - **Behavior change** The health checks of all Canton nodes (participant, sequencer and mediator) now use Canton's HTTP health endpoints
      (`/health/live` and `/health/ready`) instead of the gRPC health service. This affects:

      - Helm charts: the liveness and readiness probes of `splice-participant` and `splice-global-domain`.
        The charts enable the HTTP health endpoints on port 5071 through the `ADDITIONAL_CONFIG_HTTP_HEALTH_SERVER` environment variable.
        Set `httpHealthProbes: false` to restore the previous gRPC probes.
      - Docker images: the `HEALTHCHECK` of `canton-participant` and `canton-domain`.
        The `canton-participant` healthcheck expects the HTTP health endpoints on port 5071, which the Docker Compose deployments enable.
        If you run the `canton-participant` image with your own deployment, set
        `ADDITIONAL_CONFIG_HTTP_HEALTH_SERVER=canton.participants.participant.monitoring.http-health-server.port=5071`.
        The `canton-domain` image serves the HTTP health endpoints on ports 5071 (mediator) and 5072 (sequencer).
        The gRPC health service on port 5061 (5061 and 5062 for `canton-domain`) remains available.
      - Docker Compose deployments: the participant in the validator and SV deployments, the synchronizer node in the SV deployment,
        and the `canton` container in LocalNet.

      Liveness is unchanged. Readiness, however, now only reports ready once the node has completed its database migrations and initialized its storage.
      Previously, nodes reported ready while database migrations were still running, even though they could not serve any requests yet.
      After an upgrade with long-running database migrations, nodes therefore stay not ready (Kubernetes) or unhealthy (Docker) for the duration of the migrations.
      If you use tooling that waits for readiness, you may need to increase its timeouts, for example:

      - `helm install` and `helm upgrade` with `--wait` (default `--timeout` is 5 minutes)
      - the `progressDeadlineSeconds` of Kubernetes Deployments (default is 10 minutes), as observed by `kubectl rollout status` or GitOps tools
      - `docker compose up --wait` (including the `-w` flag of the `start.sh` scripts of the Docker Compose deployments),
        and services that depend on Canton containers with `condition: service_healthy`.
        The Docker images use a `HEALTHCHECK` start period of 10 minutes, so containers report unhealthy if migrations take longer,
        and report healthy again once the migrations are done.

  - Docker Compose deployments and localnet

    - **Breaking** The Docker Compose deployments (validator, sv and localnet) now set the default Postgres version to 18.
      Additionally, due to [upstream image's changes](https://github.com/docker-library/postgres/pull/1259) the data volume is now mounted to `/var/lib/postgresql` instead of `/var/lib/postgresql/data`.
      You should [upgrade](https://docs.canton.network/global-synchronizer/production-operations/validator-postgres-migration),
      as the previous default (14) is reaching end-of-life on November 12, 2026 and won't be supported by Splice nor receive updates from upstream Postgres.
      If you cannot yet upgrade, you must restore the previous volume in `compose.yaml` AND change the Postgres version in the `.env` file back to `14.24-trixie@sha256:8ab94f61668dc73bbab4dc13273ff2fc37e635536af62aef5306a49a9682a446`.

  - Scan App

    - The following request fields now have a `maxItems` bound of 1000; requests exceeding it are rejected with 400:

      - `/v0/open-and-issuing-mining-rounds`: `cached_open_mining_round_contract_ids`, `cached_issuing_round_contract_ids`
      - `/v2/state/acs`: `party_ids`, `templates`
      - `/v2/holdings/state`: `owner_party_ids`
      - `/v0/holdings/summary`, `/v1/holdings/summary`: `owner_party_ids`
      - `/v0/voterequest`: `vote_request_contract_ids`
      - `/v0/validators/validator-faucets`: `validator_ids`

    - Add `/v1/dso`, which returns the same DSO information as `/v0/dso` without the
      `sv_user` and `sv_party_id` fields of the SV operating the Scan instance, so that
      responses match across Scan instances. `/v0/dso` is now deprecated.

    - Add `/v0/sv-info`, which returns the `sv_user` and `sv_party_id` of the SV operating the Scan instance.

  - SV App

    - The following request fields now have a `maxItems` bound of 1000; requests exceeding it are rejected with 400:

      - `/v0/admin/sv/voterequest`: `vote_request_contract_ids`

  - Grafana

    - **Breaking**: The Grafana dashboards in the release bundle now use the V2 resource format.
      Upgrade to Grafana 13 or newer before importing them.
      Dashboard UIDs are unchanged, so existing dashboard links will keep working.

  - Validator app

     - Add `/v1/scan-proxy/dso`, which serves the DSO information from Scan's `/v1/dso`.
       `/v0/scan-proxy/dso` is deprecated: it fails when the validator is connected to more than one Scan
       instance, as the `sv_user` and `sv_party_id` fields differ between Scan instances.

     - The validator now starts automation external parties with keys embedded in a
       `PartyToParticipant` mapping by default. The prior behavior can
       be restored with the
       `canton.validator-apps.validator_backend.support-embedded-party-signing-keys = false` but it is recommended to instead make sure that the
       `ValidatorRight` contracts are [configured such that they won't start automation](https://docs.canton.network/global-synchronizer/production-operations/scalability#bypassing-the-limit).

    - Daml Model Changes:

      - Add governance locks, which implement on-chain enforcement of Featured App (FA) and Super Validator (SV)
        locking as specified in [CIP-127](https://github.com/canton-foundation/cips/blob/main/cip-0127/cip-0127.md).
        This release implements the following increments of the
        [CIP-127 incremental delivery plan](https://github.com/canton-foundation/cips/blob/main/cip-0127/cip-0127.md#incremental-delivery-plan):

        - Increment 1, compatibility mode for SV and FA locks: wallets create and manage locks via token standard
          V1 and V2 transfers to the lock manager party, as described in the
          [compatibility mode section](https://github.com/canton-foundation/cips/blob/main/cip-0127/cip-0127.md#compatibility-mode).

        - Increment 2, provisional FA locks: the Daml model supports provisional FA locks and their conversion
          into full FA locks via `DsoRules_GovernanceLock_ConvertProvisionalFeaturedAppLock`.

        Locks with custom controllers (Increment 3) are not yet supported. All locks are controlled by their owner.

      - Add an optional `governanceLockConfig` field to `AmuletConfig` with the minimum lock amount (default 10,000 CC)
        and the vesting durations for SV locks (default 365.25 days) and FA locks (default 60 days).

      - These changes require a Daml upgrade to the following versions:
